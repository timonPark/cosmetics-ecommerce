# work_history 파일 규격

## 개요

`work_history/` 폴더 안에 브랜치 단위로 생성되는 작업 기록 파일의 규격을 정의한다.  
모든 작업 기록 파일은 이 규격을 따라야 한다.

---

## 작업 분류 코드

이슈 정보의 `작업 분류` 항목에 아래 코드를 사용한다.

| 도메인 | 식별값 | 설명 |
|--------|--------|------|
| BE | `feat` | 기능 개발 — 새 API, Service 로직, DB 스키마, 외부 서비스 연동 |
| BE | `fix` | 버그 수정 — 잘못된 쿼리, 비즈니스 로직 오류, 데이터 처리 오류 |
| BE | `refactor` | 리팩토링 — 레이어 구조 개선, 코드 정리 (동작 변경 없음) |
| BE | `perf` | 성능 개선 — 쿼리 최적화, 이미지 처리 성능 |
| FE | `feat` | 화면 기능 개발 — 새 페이지, 컴포넌트, 인터랙션 구현 |
| FE | `fix` | 버그 및 기능 수정 — 잘못된 UI 동작, 렌더링 오류 수정 |
| FE | `style` | 화면 개선 및 디자인 변경 — UI/UX 개선, 스타일 변경 |
| FE | `perf` | 성능 개선 — 렌더링 최적화, 번들 최적화 |
| 공통 | `chore` | 환경 설정 — 패키지 설치, 환경변수, 빌드 설정 |
| 공통 | `docs` | 문서 작업 — CLAUDE.md, 스펙 문서, 개발 규칙 |

작성 형식: `{도메인}/{식별값}` (예: `BE/feat`, `FE/style`, `공통/docs`)

---

## 파일명 규칙

```
YYYY-MM-DD-{브랜치명}.md
```

- `YYYY-MM-DD`: 브랜치 생성일
- `{브랜치명}`: Git 브랜치명 그대로 사용 (예: `feature/#13-development-rules`)

**예시**: `2026-08-22-feature-#13-development-rules.md`

## 파일 구조 템플릿

```markdown

| 항목 | 내용 |
|------|------|
| 이슈 번호 | #{번호} |
| 이슈 제목 | {제목} |
| 이슈 URL | {URL} |
| 브랜치 | `{브랜치명}` |
| 작업 분류 | {도메인}/{식별값} (예: BE/feat, FE/style, 공통/docs) |
| 작업 시작 | YYYY-MM-DD hh:mm:ss (KST) |
| 작업 종료 | YYYY-MM-DD hh:mm:ss (KST, 머지 완료 후 업데이트) |
| 작업자 | {GitHub 계정} |

## 개요

{GitHub 이슈의 개요 내용을 그대로 옮긴다}

{GitHub 이슈의 작업 내용을 체크리스트로 옮긴다}

- [ ] 항목 2

#### 작업 내용

- {실제로 수행한 작업}

#### 결정 사항

- {작업 중 내린 기술적/구조적 결정과 그 이유}
```

## 작성 지침

- **이슈 정보**: GitHub 이슈에서 그대로 가져온다.
- **작업 분류**: 도메인(BE/FE/공통)과 식별값을 조합해 작성한다. 복수 도메인에 걸치면 `/` 로 구분해 모두 기입한다 (예: `BE/feat, FE/feat`).
- **개요 / 작업 계획 / 산출물**: GitHub 이슈 본문 내용을 복사해 시작점으로 삼는다.
- **세션 기록**: 날짜별로 섹션을 추가한다. 같은 날 여러 세션이면 하나의 날짜 섹션 안에 모두 기록한다.
- **결정 사항**: 사소해 보여도 나중에 "왜 이렇게 했지?"가 될 만한 것은 반드시 기록한다.
- **PR 정보**: 머지 완료 직후 업데이트한다.
- **시간대**: 모든 시각은 KST(UTC+9) 기준으로 기록한다. GitHub API(`mergedAt` 등)는 UTC를 반환하므로 +9시간 변환 후 입력한다.
