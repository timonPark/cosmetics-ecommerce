# 브레인스토밍: 아이디어 → 설계

자연스러운 대화를 통해 아이디어를 완전한 설계와 명세로 발전시킨다.

<HARD-GATE>
인간 파트너에게 의도를 설명하고 **명시적 승인을 받기 전까지** 구현 스킬 호출, 코드 작성, 프로젝트 스캐폴딩 등 어떤 구현 행동도 해서는 안 된다. 이는 모든 경로의 모든 작업에 적용된다. 작업 규모에 따라 절차가 달라질 뿐, 승인 게이트는 절대 생략되지 않는다.
</HARD-GATE>

## 세 가지 경로

첫 번째 질문 전에 요청을 분류하고, 분류 결과를 소리 내어 말한다:

- **Spike** — 가능성 탐색 질문("할 수 있는지", "간단히만 확인하면 되는지"). 결과물은 코드가 아닌 답변이다. 2-3문장으로 탐색 계획을 제시하고 승인을 받은 후 최소한의 비용으로 조사한다. 설계 문서나 스펙 파일 없음. 결과는 권고안으로 보고하며, 작성된 코드는 throwaway로 표시한다.
- **Bounded** — 이미 존재하는 코드에 대한 명확히 범위가 정해진 변경(새 플래그, 작은 엔드포인트, 단일 파일 수정). 기존 코드 흐름이 레포에 있을 때만 bounded다. 없으면 architectural이다. 핵심 질문 후 짧은 설계를 채팅에 제시하고 멈춘다. 스펙 파일이나 구현 계획 문서 없음.
- **Architectural** — 새 프로젝트, 새 서브시스템, 컴포넌트 구조 변경. 전체 프로세스를 따른다: 질문 → 접근법 제안 → 섹션별 설계 → 스펙 작성 → `/write-plan` 호출.

의심스러울 때는 더 무거운 경로를 택한다. 작업 도중 숨겨진 복잡도가 발견되면 경로를 업그레이드한다 — 멈추고, 말하고, 올라간다. 다운그레이드는 없다.

## 안티패턴: "너무 간단해서 승인이 필요 없다"

모든 경로는 구현 전 승인으로 끝난다. todo 목록, 단일 함수 유틸리티, 설정 변경 — 설계가 두 문장이어도 반드시 제시하고 승인을 받아야 한다. 단순한 작업일수록 검토되지 않은 가정이 낭비를 만든다.

## Red Flags

| 생각 | 현실 |
|------|------|
| "너무 간단해서 설계가 필요 없다" | 단순하면 짧은 설계, 설계 없음이 아니다. 채팅에 두 문장, 그리고 승인. |
| "bounded로 분류하고 스펙을 건너뛰겠다" | 레이블로 작업을 회피하려는 것 자체가 의심 신호 — 더 무거운 경로를 택한다. |
| "bounded고 설계가 명백하니 읽는 동안 시작하겠다" | 게이트는 설계의 길이가 아닌 승인이다. 제시하고, 멈추고, yes를 기다린다. |
| "이런 종류의 앱을 알아서 bounded다" | bounded는 레포를 기준으로 측정한다. 새 프로젝트에는 기존 흐름이 없으므로 architectural이다. |
| "spike가 작동하니 코드를 유지하겠다" | spike의 결과물은 답변이다. 코드를 유지하는 것은 새 요청이므로 분류한다. |
| "거의 다 됐으니 재분류할 필요 없다" | 숨겨진 복잡도는 경로를 업그레이드한다. 멈추고 말한다. |
| "spike를 승인받았으니 후속 변경도 승인된 것이다" | 각 작업은 별도의 분류와 별도의 승인을 받는다. |

## 체크리스트

분류 후 경로를 선언하고, 각 항목에 대해 TaskCreate로 작업을 생성한 뒤 순서대로 완료한다.

**Spike:**
1. 프로브 구성을 위한 프로젝트 컨텍스트 탐색
2. 질문 + 탐색 계획 제시 (2-3문장)
3. 승인 받기
4. 조사 — 정확성이 허용하는 최소한의 비용으로
5. 결과 보고 — 권고안; 작성된 것은 throwaway로 표시

**Bounded:**
1. 프로젝트 컨텍스트 탐색 — 파일, 문서, 최근 커밋 확인
2. 핵심 질문 하기 — 한 번에 하나씩
3. 채팅에 짧은 설계 제시 — 접근법, 수정 파일, 테스트
4. 승인 받기 — 멈추고 명시적 yes를 기다린다
5. 구현 — 일반 개발 워크플로우 진행; 계획 문서 없음

**Architectural:**
1. 프로젝트 컨텍스트 탐색 — 파일, 문서, 최근 커밋 확인
2. 명확화 질문 — 한 번에 하나씩, 목적/제약/성공 기준 파악
3. 2-3가지 접근법 제안 — 트레이드오프와 권고안 포함
4. 설계 제시 — 복잡도에 따른 섹션 단위, 각 섹션 후 승인 확인
5. 설계 문서 작성 — `docs/specs/YYYY-MM-DD-<topic>-design.md` 에 저장 후 커밋
6. 스펙 셀프 리뷰 — 플레이스홀더, 모순, 모호함, 범위 점검
7. 사용자 리뷰 게이트 — 스펙 파일 검토 요청, 변경 반영 후 승인 확인
8. `/write-plan` 호출 — 구현 계획 작성으로 전환

## 프로세스 상세

### 아이디어 이해

- 먼저 현재 프로젝트 상태 파악 (파일, 문서, 최근 커밋)
- 세부 질문 전에 범위 평가: 여러 독립 서브시스템을 설명하면 즉시 분해 필요성을 알린다
- 범위가 너무 크면 서브프로젝트로 분해를 도운다 — 각 서브프로젝트는 자체 스펙 → 계획 → 구현 사이클을 가진다
- 질문은 한 번에 하나씩, 가능하면 선택지 형태로
- 목적, 제약, 성공 기준에 집중

### 접근법 탐색

- 2-3가지 접근법을 트레이드오프와 함께 제안
- 권고안을 먼저 제시하고 이유 설명
- YAGNI를 철저히 적용 — 모든 접근법과 설계에서 불필요한 기능 제거

### 설계 제시

- 설계를 이해했다고 판단되면 제시
- 각 섹션을 복잡도에 비례하여 작성: 간단하면 몇 문장, 복잡하면 200-300단어
- 아키텍처, 컴포넌트, 데이터 흐름, 에러 처리, 테스트 커버
- 각 섹션 후 "지금까지 괜찮은가요?" 확인

### 격리와 명확성을 위한 설계

- 단일 명확한 목적, 잘 정의된 인터페이스, 독립적으로 이해·테스트 가능한 단위로 분리
- 각 단위에 대해 답할 수 있어야 한다: 무엇을 하는가, 어떻게 사용하는가, 무엇에 의존하는가?
- 파일이 커지면 너무 많은 일을 하고 있다는 신호다

### 기존 코드베이스에서 작업

- 변경 전 현재 구조 탐색. 기존 패턴을 따른다.
- 작업에 영향을 주는 기존 코드 문제(너무 커진 파일, 불명확한 경계 등)는 설계의 일부로 포함
- 관련 없는 리팩토링은 제안하지 않는다. 현재 목표에 집중한다.

## 설계 완료 후 (architectural 경로)

**문서화:**
- 검증된 설계(스펙)를 `docs/specs/YYYY-MM-DD-<topic>-design.md` 에 저장
- 설계 문서를 git에 커밋

**스펙 셀프 리뷰:**
1. **플레이스홀더 스캔**: "TBD", "TODO", 미완성 섹션, 모호한 요구사항 → 수정
2. **내부 일관성**: 섹션 간 모순? 아키텍처와 기능 설명이 일치하는가?
3. **범위 점검**: 단일 구현 계획으로 충분히 집중되어 있는가?
4. **모호함 점검**: 두 가지로 해석 가능한 요구사항 → 하나를 선택해 명시

인라인으로 수정한다. 재검토 불필요 — 수정하고 넘어간다.

**사용자 리뷰 게이트:**
스펙 리뷰 통과 후 사용자에게 검토 요청:

> "스펙을 `<경로>`에 작성하고 커밋했습니다. 구현 계획 작성 전에 검토해주세요."

사용자 응답을 기다린다. 변경 요청 시 반영 후 스펙 리뷰를 재실행한다. 승인 후에만 진행한다.

**구현:**
- `/write-plan`을 호출해 상세 구현 계획 작성으로 전환
- 다른 스킬은 호출하지 않는다. `/write-plan`이 다음 단계다.
