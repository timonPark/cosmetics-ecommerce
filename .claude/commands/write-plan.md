# 구현 계획 작성

## 개요

코드베이스에 대한 컨텍스트가 전혀 없는 엔지니어를 가정하고 완전한 구현 계획을 작성한다. 어떤 파일을 건드려야 하는지, 테스트 방법, 참고 문서까지 모두 담는다. DRY. YAGNI. TDD. 잦은 커밋.

숙련된 개발자이지만 이 프로젝트의 툴셋과 도메인은 거의 모른다고 가정한다.

**시작 시 선언:** "구현 계획을 작성하기 위해 write-plan 스킬을 사용합니다."

**계획 저장 위치:** `docs/plans/YYYY-MM-DD-<feature-name>.md`

## 범위 점검

스펙이 여러 독립 서브시스템을 다루고 있다면 `/brainstorm` 단계에서 분리됐어야 한다. 그렇지 않다면 서브시스템당 하나씩 별도 계획으로 나눌 것을 제안한다. 각 계획은 단독으로 작동하고 테스트 가능한 소프트웨어를 산출해야 한다.

## 파일 구조 정의

태스크를 정의하기 전에 생성/수정할 파일과 각 파일의 책임을 먼저 정리한다.

- 명확한 경계와 잘 정의된 인터페이스를 가진 단위로 설계한다. 파일당 하나의 명확한 책임.
- 함께 변경되는 파일은 함께 위치한다. 기술 레이어가 아닌 책임 단위로 분리한다.
- 기존 코드베이스에서는 확립된 패턴을 따른다.
- 파일이 너무 커졌다면 분리를 계획에 포함하는 것이 합리적이다.

이 구조가 태스크 분해의 기반이 된다. 각 태스크는 독립적으로 의미 있는 변경을 산출해야 한다.

## 태스크 크기 기준

태스크는 자체 테스트 사이클을 가지고 독립적으로 검토 가능한 최소 단위다. 설정, 스캐폴딩, 문서화 단계는 해당 결과물이 필요한 태스크에 포함한다. 리뷰어가 한 태스크는 승인하고 다른 태스크는 거부할 수 있는 경우에만 분리한다. 각 태스크는 독립적으로 테스트 가능한 결과물로 끝난다.

## 단계 세분화

**각 스텝은 하나의 행동 (2-5분):**
- "실패하는 테스트 작성" — 스텝
- "실패 확인을 위해 실행" — 스텝
- "테스트를 통과시키는 최소 코드 구현" — 스텝
- "테스트 통과 확인을 위해 실행" — 스텝
- "커밋" — 스텝

## 계획 문서 헤더

**모든 계획은 반드시 이 헤더로 시작한다:**

```markdown
# [기능명] 구현 계획

**목표:** [이것이 무엇을 만드는지 한 문장]

**아키텍처:** [접근 방식 2-3문장]

**기술 스택:** [핵심 기술/라이브러리]

**스펙:** [이 계획이 구현하는 설계 문서 경로]

## 전역 제약

[프로젝트 전체 요구사항 — 버전 하한, 의존성 제한, 네이밍 규칙 등 한 줄씩, 스펙에서 그대로 복사]

---
```

## 태스크 구조

````markdown
### 태스크 N: [컴포넌트명]

**파일:**
- 생성: `exact/path/to/file.ts`
- 수정: `exact/path/to/existing.ts`
- 테스트: `exact/path/to/file.test.ts`

**인터페이스:**
- 소비: [이 태스크가 이전 태스크에서 사용하는 것 — 정확한 시그니처]
- 생산: [이후 태스크가 의존하는 것 — 정확한 함수명, 파라미터, 반환 타입]

- [ ] **스텝 1: 실패하는 테스트 작성**

```typescript
it('should 구체적인 동작', () => {
  const result = functionName(input)
  expect(result).toBe(expected)
})
```

- [ ] **스텝 2: 테스트 실패 확인**

실행: `pnpm test path/to/file.test.ts`
예상: FAIL — "functionName is not defined"

- [ ] **스텝 3: 최소 구현 작성**

```typescript
export function functionName(input: Type): ReturnType {
  return expected
}
```

- [ ] **스텝 4: 테스트 통과 확인**

실행: `pnpm test path/to/file.test.ts`
예상: PASS

- [ ] **스텝 5: 커밋**

```bash
git add path/to/file.ts path/to/file.test.ts
git commit -m "feat: 구체적인 기능 추가 closes #이슈번호"
```
````

## 플레이스홀더 금지

모든 스텝은 엔지니어가 필요한 실제 내용을 담아야 한다. 다음은 **계획 실패** — 절대 작성하지 않는다:
- "TBD", "TODO", "나중에 구현", "세부사항 채우기"
- "적절한 에러 처리 추가" / "유효성 검사 추가" / "엣지 케이스 처리"
- "위에 대한 테스트 작성" (실제 테스트 코드 없이)
- "태스크 N과 유사" (엔지니어가 순서 없이 읽을 수 있으므로 코드를 반복한다)
- 어떻게 해야 하는지 코드 없이 설명만 하는 스텝

## 셀프 리뷰

완전한 계획 작성 후 스펙과 대조하여 점검한다.

**1. 스펙 커버리지:** 스펙의 각 섹션/요구사항을 훑는다. 구현하는 태스크를 가리킬 수 있는가? 누락된 항목을 나열한다.

**2. 플레이스홀더 스캔:** 위 "플레이스홀더 금지" 패턴을 검색한다. 발견 시 수정한다.

**3. 타입 일관성:** 이후 태스크에서 사용한 타입, 메서드 시그니처, 프로퍼티명이 이전 태스크에서 정의한 것과 일치하는가? 불일치는 버그다.

문제 발견 시 인라인으로 수정한다. 재검토 불필요 — 수정하고 넘어간다. 스펙 요구사항에 대응하는 태스크가 없으면 태스크를 추가한다.

## 실행 전환

계획 저장 후 실행 방식을 제안한다:

> "계획을 `docs/plans/<파일명>.md`에 저장했습니다. 두 가지 실행 방식이 있습니다.
>
> **1. 서브에이전트 방식 (권장)** — 태스크별로 독립 에이전트를 디스패치, 태스크 사이에 리뷰 가능, 빠른 반복
>
> **2. 인라인 실행** — 현재 세션에서 태스크를 순서대로 실행, 체크포인트마다 리뷰
>
> 어떤 방식으로 진행할까요?"
