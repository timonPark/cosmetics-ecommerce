# GitHub 프로젝트 관리 규칙

이 문서는 두 가지 용도로 사용한다:
- **사람**: GitHub 작업(이슈 등록, 라벨·마일스톤 배정, PR 생성) 전 참고
- **Claude**: GitHub 관련 요청 수행 시 따르는 행동 지침

---

## 1. 라벨 규칙

이슈 등록 시 아래 6개 라벨 중 **하나**를 반드시 지정한다.

| 라벨 | 사용 조건 |
|------|-----------|
| `setup` | 환경 세팅, 패키지 설치, CI/CD 설정 등 개발 인프라 준비 |
| `feature` | 새 기능 개발 (화면, API, 서비스 로직) |
| `bug` | 기존 동작의 오류 수정 |
| `design` | UI/UX 디자인, Figma 작업, 스타일 변경 |
| `infra` | 배포, 도메인, 서버·DB 인프라 운영 |
| `data` | 크롤링 데이터 마이그레이션, 스키마 설계, 데이터 정제 |

**라벨이 두 개 이상 해당되면** 더 핵심적인 하나만 선택한다:
- 코드 작성이 주목적 → `feature`
- 환경/도구 설정이 주목적 → `setup`
- 데이터 이동·변환이 주목적 → `data`
- 배포·운영 인프라가 주목적 → `infra`

## 2. 마일스톤 규칙

이슈 등록 시 아래 4개 마일스톤 중 하나를 지정한다.

| 마일스톤 | 포함 범위 | 배정 기준 |
|----------|-----------|-----------|
| `v0.1 - 인프라 세팅` | 0단계(GitHub 세팅), 1단계(개발 환경), 2단계(데이터/백엔드), 3단계(크롤링 마이그레이션) | 서비스를 만들기 위한 기반 준비 |
| `v0.2 - 핵심 기능` | 4단계(핵심 기능 개발) | 사용자가 직접 사용하는 기능 |
| `v0.3 - 배포/점검` | 5단계(배포), 6단계(마무리 점검) | Vercel 배포, 도메인, 모니터링 |
| `v1.0 - 오픈` | 정식 오픈 | 모든 마일스톤 완료 후 |

기능 개발이더라도 "첫 배포 전 필수 기반 작업"이면 → `v0.1`

## 3. 이슈 등록 규칙

### 3-1. 상위 이슈 → 하위 이슈 구조

큰 작업 단위는 **상위 이슈**로, 세부 작업은 **하위 이슈(Sub-issue)**로 연결한다.

```
상위 이슈 (#1): "1. 개발 환경 초기 세팅"
├── 하위 이슈 (#7): "Next.js 15 프로젝트 생성"
├── 하위 이슈 (#8): "Tailwind CSS + shadcn/ui 설치"
└── 하위 이슈 (#9): "CLAUDE.md 작성"
```

- 상위 이슈 본문에 하위 이슈 목록을 체크박스로 나열하고, 하위 이슈 생성 후 번호를 링크로 연결한다
- 하위 이슈 머지 완료 후 상위 이슈 체크박스를 수동으로 체크한다
- 상위 이슈는 모든 하위 이슈 완료 후 수동으로 닫는다 (`closes`로 자동 닫지 않는다)

### 3-2. 이슈 제목 포맷

```
{도메인}/{식별값}: {작업 내용}
```

| 도메인 | 식별값 | 예시 |
|--------|--------|------|
| `BE` | `feat`, `fix`, `refactor`, `perf` | `BE/feat: 상품 조회 Service 구현` |
| `FE` | `feat`, `fix`, `style`, `perf` | `FE/feat: 상품 목록 페이지 구현` |
| `공통` | `chore`, `docs` | `공통/chore: Jest 테스트 환경 세팅` |

### 3-3. 이슈 템플릿 선택

- **기능 요청 템플릿**: `feature`, `setup`, `design`, `infra`, `data` 라벨 이슈
- **버그 리포트 템플릿**: `bug` 라벨 이슈

### 3-4. Assignees 지정

이슈 생성 시 반드시 작업 담당자를 Assignees에 지정한다. 담당자 미지정 금지.

## 4. 브랜치-이슈 연결 규칙

### 4-1. 브랜치 생성

이슈 생성 직후 브랜치를 만든다. 반드시 `dev` 기반으로 생성한다.

```bash
git checkout -b feature/#이슈번호-작업명 dev
# 예시: git checkout -b feature/#15-jest-setup dev
```

브랜치명 규칙:
- 일반 작업: `feature/#이슈번호-작업명`
- 프로덕션 긴급 수정: `hotfix/#이슈번호-작업명` (main 기반으로 생성)
- 작업명: kebab-case, 영문 또는 한글 축약 허용

### 4-2. `closes #이슈번호` 표기 위치

| 위치 | 언제 사용 |
|------|-----------|
| **PR 본문** (권장) | 대부분의 경우. PR 머지 시 이슈 자동 닫힘 |
| **커밋 메시지** | 단일 커밋으로 완결되는 매우 작은 작업 |

- 하나의 PR이 여러 이슈를 닫을 경우: `closes #15, closes #16`
- 상위 이슈는 `closes`로 연결하지 않는다. 모든 하위 이슈 완료 후 수동으로 닫는다.

## 5. GitHub Project Status 규칙

GitHub Project(timonPark/projects/11)의 Status 필드를 작업 단계에 맞게 업데이트한다.

| Status | 설정 시점 |
|--------|-----------|
| `Todo` | 이슈 생성 직후 Project에 추가할 때 (기본값) |
| `In Progress` | feature 브랜치 생성 후 작업 시작 시 |
| `Done` | PR 머지 완료 시 |

**규칙**:
- 이슈를 생성한 직후 반드시 GitHub Project에 추가한다. Status는 `Todo`로 설정한다.
- 브랜치를 생성하고 작업을 시작하면 즉시 `In Progress`로 변경한다
- PR이 dev에 머지되면 `Done`으로 변경한다

## 6. 작업 흐름 체크리스트

GitHub 작업을 시작할 때 아래 순서를 그대로 따른다.

### 작업 시작

- [ ] GitHub에 이슈 생성 (제목 포맷, 라벨, 마일스톤, Assignees 지정)
- [ ] 이슈 생성 직후 GitHub Project(timonPark/projects/11)에 추가 (Status: `Todo`)
- [ ] 상위 이슈가 있으면 Sub-issue로 연결
- [ ] GitHub Project에서 이슈 Status → `In Progress` 로 변경
- [ ] `dev` 기반으로 feature 브랜치 생성
- [ ] 브랜치 생성 즉시 `work_history/YYYY-MM-DD-{브랜치명}.md` 파일 생성 및 기록 시작

### 작업 중

- [ ] 커밋 메시지 포맷: `{도메인}/{식별값}: {내용}`
- [ ] 결정 사항, 특이사항은 work_history에 즉시 기록

### 작업 완료

- [ ] `git push origin {브랜치명}` 후 PR 생성
- [ ] PR 제목: 커밋 메시지와 동일한 포맷
- [ ] PR 본문에 `closes #이슈번호` 표기
- [ ] `dev` ← feature 브랜치 방향으로 PR 생성
- [ ] PR 머지 완료 후 GitHub Project Status → `Done` 으로 변경
- [ ] PR 머지 완료 후 work_history 파일에 PR URL 및 머지 완료일 업데이트

### hotfix (프로덕션 긴급 수정 시만)

- [ ] `main` 기반으로 `hotfix/#이슈번호-작업명` 브랜치 생성
- [ ] 수정 완료 후 `main` ← hotfix PR 머지
- [ ] `dev` ← hotfix PR 머지 (양쪽 모두 반영)

## 7. Claude Code 분류기 관련 참고

Claude Code의 auto mode classifier가 `.claude/commands/` 경로를 간헐적으로 차단할 수 있다.

**git push 차단 시**: `git push`가 차단되면 `git push origin {브랜치명}`으로 브랜치를 명시해서 재시도한다.
